A notebook for connecting the dots

Security learning and infrastructure work meet in a surprisingly ordinary place: a question that cannot be answered confidently yet. Why does this service need that permission? What changed before the alert appeared? Does this check demonstrate that a control works, or does it only show that a command completed? A useful notebook gives those questions somewhere to live. It preserves the reasoning around an observation instead of leaving a collection of commands without context.

My background includes AWS infrastructure, Linux administration, GitHub Actions, identity and access management, and security automation. I also practise on TryHackMe as cyberhitman. On 3 October 2026, that profile showed a top 1% ranking, 290 completed rooms, and 53 badges. Those figures describe activity on a learning platform. They are a starting point for this notebook, not a substitute for explaining a system or demonstrating the quality of a security decision.

The aim here is to connect learning with useful engineering habits. A lab can make a vulnerability understandable. A system audit can make the importance of documentation obvious. A deployment pipeline can show why an apparently small permission deserves careful review. Writing about these connections creates a record that can be revisited when the original environment is gone and the details have become difficult to remember.

This first post sets out an approach to that record. It combines the professional and academic background listed in my resume with topics visible on my public profiles, then develops a practical method for studying and documenting security. The study plans, example questions, and suggested exercises below are proposals for this notebook. They should not be read as claims that every exercise has already been completed.

A public notebook also changes the standard for an explanation. A private reminder can say “check the role.” A useful public note needs to say which role, what access is expected, what evidence was reviewed, and what remains uncertain. That extra precision is valuable even when nobody else reads the page.

Where the infrastructure background fits

The supplied resume lists a DevSecOps internship at AndOr Communication from March to September 2025, followed by a DevSecOps Engineer role from September 2025. The described work includes GitHub Actions pipelines, AWS EC2, S3 and IAM environments, Linux administration, repository access, monitoring, encryption, secrets management, vulnerability assessments, and server hardening. These responsibilities provide the practical context for a notebook concerned with the systems around an application.

That context matters because security rarely belongs to a single component. An application may be carefully written while its deployment identity has unnecessary access. A server may have current packages while an operational script exposes information in a log. A repository may require reviews while a workflow permits unreviewed code to reach a privileged environment. Understanding those relationships requires looking across development, operations, and security rather than treating them as isolated subjects.

One useful way to organise a learning question is to ask who owns the decision. Developers may know why an application needs an API. Infrastructure engineers may know where its network traffic goes. Security reviewers may know which assumptions deserve an explicit test. The person writing the note does not need to pretend to know everything; the note becomes stronger when it identifies whose input is needed and what evidence would settle the question.

The transition from an exercise to an operational environment also introduces constraints. A lab can often be reset quickly. A real service has users, release schedules, dependencies, and recovery requirements. A technically correct change can still create an incident if its effect is not understood. For that reason, this notebook will distinguish observation from intervention, and a proposed improvement from a change that has actually been implemented and verified.

Experience should guide the questions without becoming a source of exaggerated claims. A resume can establish that a person worked on vulnerability assessment. It does not prove that every vulnerability was resolved or that an organisation is secure. Good writing preserves that distinction. It describes the work at the level supported by the source and uses examples to explore a concept without attributing invented outcomes to an employer.

What a learning profile can and cannot show

TryHackMe provides an environment in which security topics can be studied through guided material and practical exercises. My visible completed-room list includes Introduction to DevSecOps, SSDLC, Dependency Management, Linux Fundamentals Part 1, and several topics concerning AI security. This makes those subjects reasonable starting points for the site. It does not establish that a particular certification has been earned, that an unseen room has been completed, or that a specific attack was used in professional work.

A ranking can provide encouragement, but it is an incomplete description of learning. It does not show whether an explanation is clear, whether an unfamiliar problem can be investigated, or whether a proposed control remains effective after a system changes. Those are useful questions to bring into a notebook because they move attention from completion toward understanding. A badge is visible evidence of platform progress; a careful explanation is evidence of reasoning.

There is also a difference between recognising an answer and reconstructing a method. A room can supply the next step. A later problem may only supply a symptom. To bridge that gap, a note should preserve the reason for choosing an observation, the alternative explanations considered, and the evidence that ruled an explanation out. That makes the method easier to reuse when the next exercise has different names, addresses, or tools.

For example, a completed topic on dependency management suggests useful questions about how a build chooses package versions and where a package comes from. It does not justify a fictional account of discovering a supply-chain compromise. The notebook can explore the questions directly, link to the learning topic, and build a small original example. That produces a useful article without turning a course title into an invented personal story.

Finally, learning statistics change. The profile figures on this site are labelled with the date on which they were checked, and the live profile remains linked. A reader can follow that link for current activity. A dated snapshot is more honest than a static number presented as a live feed, especially when the notebook has no automatic connection to the learning platform.

A study cycle that ends with an explanation

A proposed study cycle for this notebook has five stages: frame a question, establish a small environment, make an observation, interpret the result, and write the explanation. The stages are simple on purpose. They help keep the exercise directed toward a learning outcome while leaving room for surprises. A session does not have to produce a successful exploit or a completed project to produce a useful note.

Framing the question is the most useful place to slow down. “Learn Linux security” is too broad for one session. “Understand which identity owns this process and which resources it can access” is much easier to investigate. The narrower question also makes it possible to recognise progress. If the session ends with a clear explanation of process identity and an unresolved question about group membership, the next session has a meaningful starting point.

The environment should be small enough that the result can be explained. Introducing several new services at once can create a demonstration that works while leaving the important behaviour hidden. A disposable lab with one application, one identity, and one storage location may teach more about an access boundary than a large stack assembled from a tutorial. Complexity can be added after the initial relationship is understood.

Observation comes before interpretation. Record what the system actually returned, which configuration was in place, and which assumptions were made. Then ask what the result supports. A denied request may indicate a useful control, but it may also indicate a broken path, an incorrect account, or a configuration unrelated to the intended test. Writing the observation separately makes those alternatives easier to consider.

The final explanation should be readable without access to the original screen. It needs enough context to understand the question and enough detail to repeat the relevant part of the exercise. It should also say where the explanation stops. If a result was demonstrated only in one lab configuration, that boundary belongs in the note. Finishing with a bounded explanation is a better learning outcome than finishing with a screenshot whose meaning has already started to fade.

Writing a lab note another person can use

A useful lab note begins with scope. Name the learning environment, the topic, the intended question, and the conditions under which the exercise was performed. Avoid publishing addresses or credentials that belong to an employer or another person. For public learning material, a small fictional environment or a platform-provided target usually makes the concept easier to explain while keeping the note focused on the mechanism.

The body can then follow a consistent pattern: expected behaviour, observed behaviour, interpretation, and verification. Expected behaviour describes the control or system property being studied. Observed behaviour records the result. Interpretation explains the connection between the two. Verification asks whether another observation supports the conclusion. This pattern works for a permissions exercise, a deployment review, or a basic log-analysis investigation.

Suppose a lab application should read one configuration file but should not change it. A weak note might record only that the application started. A stronger note would explain the process identity, the file ownership, the expected read access, and an attempted write that should fail. It would also distinguish an application error from an operating-system access decision. The extra detail makes the control visible rather than assuming that startup proves correctness.

Keep a separate space for unresolved questions. Perhaps the test did not cover a second process identity. Perhaps a reboot might change the result. Perhaps the configuration was inherited from a base image that has not been examined. These are not defects to hide. They are boundaries that allow a later reader to assess the note accurately and allow the author to plan a more focused follow-up.

Commands and screenshots should support the explanation, not take its place. Include a command when its flags are necessary to understand the result, and explain what those flags mean in this context. Include a screenshot when it shows a relevant state that would otherwise be difficult to describe. Remove repetitive output, unrelated tabs, and personal information. The reader should be able to find the evidence quickly instead of searching a transcript for the important line.

Linux as a place to learn system boundaries

Linux is a useful foundation for this notebook because it makes many security boundaries concrete. Processes have identities. Files have owners and permissions. Services have configuration and startup behaviour. Logs describe selected events. Each of these subjects can be studied in a small environment, and each can be connected to a question about how a larger system should behave.

A proposed permissions exercise could start with a deliberately simple scenario: one user creates a file, another user needs to read it, and neither should have unnecessary write access. The useful learning outcome is an explanation of why the result occurs, not a memorised command. The note should describe the ownership and group relationship, show the relevant access outcome, and identify what would change if the file were replaced or moved.

Service administration introduces another set of questions. Which account runs the service? Which directories can it change? What configuration is read at startup? Where does the service record errors? A notebook can turn these questions into a small inventory rather than applying a collection of hardening changes without an explanation. The inventory becomes a baseline for deciding whether a later change is expected.

Hardening should also preserve function. A control that prevents an application from starting may reduce one kind of exposure while making the service unusable. That outcome deserves analysis, not an automatic declaration of success. A proposed change should include an expected security effect and a functional check. If the result is uncertain, document it and return to the smallest environment that reproduces the behaviour.

The university security-automation project listed in my resume provides a practical anchor for this interest. It involved EC2 lab nodes, OpenVAS scans, CloudWatch log observations, Bash checks, and a hardening runbook. This notebook can develop the documentation habits associated with that kind of work while keeping new exercises separate from the historical project. A future article should say explicitly whether it describes that project, a later lab, or an illustrative example prepared for teaching.

Cloud learning starts with identity and ownership

Cloud infrastructure can make it easy to create resources before their relationships are understood. A more useful learning exercise starts with identity, ownership, and intended access. Who is requesting an operation? Which resource is involved? Why should the request succeed? What should remain unavailable? These questions help connect a cloud console view with the access decisions that matter to a system.

The notebook can separate three kinds of evidence. Configuration evidence describes the policies and resource settings visible at a particular time. Behavioural evidence describes the outcome of a request made under defined conditions. Operational evidence describes what happened in an environment over time. A configuration review and an access test can complement one another, but neither should be described as if it answers every question about an environment.

Consider a fictional application that needs to read a single object from storage. The learning goal could be to describe the relationship between its runtime identity and that object. Begin with a diagram of the intended request. Then record the exact resource scope and the observed outcome. A separate exercise can examine how deployment changes the identity. Keeping the questions separate reduces the temptation to grant broad access simply to make a demonstration work.

Ownership also matters for maintenance. A resource can exist without anyone remembering why it was created. A proposed cloud note should therefore record the purpose of the resource, the owner of the access decision, and the condition under which the resource can be removed. These details make a lab easier to clean up and make the reasoning more useful when studying infrastructure management.

This is an area where personal lab material and professional material need a clear boundary. Public notes should use authorised learning environments and avoid reproducing confidential architecture. The goal is to explain a reusable idea, such as a narrow access relationship or a documented configuration baseline. The value comes from the clarity of the reasoning, not from revealing the names or layout of systems that readers do not need to know.

Seeing a delivery pipeline as a security system

A delivery pipeline connects several decisions that are often discussed separately. It accepts a change, selects dependencies, runs tools, produces an artifact, and may publish that artifact to an environment. Studying the pipeline as a whole makes it possible to ask where trust is introduced and where a decision can be reviewed. This is the connection explored in the technical article that accompanies this post.

The completed TryHackMe topics on DevSecOps, secure development, and dependency management provide relevant subject matter, while the resume’s GitHub Actions experience provides practical context. The notebook should connect these sources carefully. A course establishes that a topic was studied; a resume describes professional responsibilities. Neither source should be stretched into a claim that a particular production architecture was used unless that architecture is independently documented.

For a learning exercise, draw the pipeline before writing the workflow. Label the input to each stage, the identity that runs it, and the output that leaves it. Mark the places where an untrusted change can execute and the places where publishing becomes possible. Even a static website has these relationships. Its build may need only repository read access, while its publication step needs a different authority.

The next question is how to recognise a failure. A build can pass while publishing the wrong folder. A deployment can report success while a reader sees an older version. A useful learning note therefore follows the result all the way to the public page or running service. It records the source revision, the produced artifact, and the visible behaviour. This prevents “the command succeeded” from becoming the end of the investigation.

There is also a writing lesson here. The pipeline explanation should name the decisions the reader can assess, such as whether a pull request can access deployment credentials. It should avoid turning a workflow file into a wall of unexplained configuration. A small annotated fragment, a clear diagram, and a verification method often teach more than a complete pipeline pasted without context.

Automation should preserve the evidence

Automation is valuable when it makes a useful check repeatable. It can also make a weak assumption repeatable. Before turning a command into a script, decide what the result means, how failure should be reported, and what a person needs to investigate. A script that prints a green label because a tool ran successfully may hide the fact that the intended control was never tested.

The security-automation laboratory project in my resume included Bash checks for permissions, open ports, and failed logins, along with a documented hardening runbook. Those subjects illustrate the importance of defining a check. A port being open is an observation. Whether it is expected depends on the service, the interface, the environment, and the intended access. A useful report keeps the observation and the interpretation distinguishable.

A proposed notebook exercise could design a report with three outcomes: the expected condition was observed, an unexpected condition was observed, or the check could not establish a result. That third outcome matters. Missing permissions, an unavailable log, or a failed tool invocation should not silently become a pass. Naming uncertainty allows a person to decide whether the check should be rerun or the investigation should change direction.

Repeatability also needs stable inputs. Record the environment, the version of the check, and the configuration it assumes. If a check depends on a particular path or service name, put that dependency in the explanation. When the environment changes, the report can then explain why an earlier conclusion may no longer apply. A reliable script is easier to maintain when its assumptions are visible.

Finally, automation should make the next action clearer. A finding should point to evidence, identify its scope, and suggest a responsible owner. It should avoid making an irreversible change merely because a condition looked unusual. Observation and remediation can be separate steps, particularly in learning material. That separation helps a reader understand what was discovered before considering what should be changed.

Turning an offensive observation into a defensive question

An offensive learning exercise can reveal how a boundary fails. A defensive note asks what would help identify, prevent, or investigate that failure. The connection is most useful when it stays specific. “Monitor everything” is difficult to assess. “Record which identity requested this operation and whether the request succeeded” gives a reader a concrete observation to look for.

One proposed method is to write two descriptions of the same fictional scenario. The first follows the actor trying to cross a boundary. The second follows the defender trying to understand the evidence left behind. Neither description needs to include a harmful payload. The goal is to identify the system behaviour, the relevant records, and the point at which a decision could interrupt the sequence.

The defender’s description should also account for normal activity. A failed request can occur because of a mistake, an expired configuration, or a deliberate test. A useful investigation considers the surrounding context rather than assigning an intent to one isolated event. The notebook can list competing explanations and say which additional observation would help distinguish them. This is a practical way to make uncertainty part of the method.

Detection ideas should be treated as hypotheses until tested. A rule that appears sensible on paper may miss a different version of the behaviour or produce too many ordinary events to be useful. A small authorised lab can help study that trade-off. Document the examples used, the result, and the limitations of the sample. Avoid describing a classroom demonstration as evidence of effectiveness across an entire organisation.

This perspective gives lab writeups a second life. A reader interested in defence can use the note to understand a control, while a learner can use it to understand the original mechanism. The same page can serve both audiences if it clearly separates the observation, the explanation, and the proposed response. That structure is more durable than a writeup whose only outcome is a challenge answer.

Studying AI security without losing the system around it

The supplied resume also describes an academic MRI image-classification project using TensorFlow and Keras. Together, these sources explain why AI security belongs in the notebook. They do not establish that a research result has been validated for operational security use.

The MRI project offers a useful reminder about evaluation. A model result depends on the dataset, the split, the labels, and the measurement method. A number without those details is difficult to interpret. When studying security applications of machine learning, the notebook should therefore describe the task, the available data, and the cost of different mistakes before discussing a score.

A proposed exercise might use a small labelled dataset to explore whether a model distinguishes two kinds of log event. The first questions should concern the labels and the sample, not the architecture. Are examples duplicated? Does the training data contain information that would not be available at prediction time? Does the evaluation represent the environment in which the system would be used? These questions turn an attractive demonstration into an investigation.

AI systems also sit inside ordinary infrastructure. They have storage, package dependencies, runtime identities, network interfaces, and deployment processes. A notebook about AI security should not skip these relationships merely because the model is interesting. A diagram of data movement and access can reveal questions that a model metric cannot answer, including who can replace an artifact or change an input source.

The visible TryHackMe room list includes AI supply-chain and threat-modelling topics, which provide further directions for learning. Future notes can examine those themes through clearly labelled exercises. They should state whether an example is a conceptual model, a local demonstration, or an evaluated result. That distinction keeps the notebook useful to readers who need to understand the evidence behind a security claim.

Collaboration adds an important test of clarity. If another team member cannot identify the expected result from a document, the document may be relying too heavily on shared memory. A project explanation should identify the role of each component without requiring the reader to reconstruct the architecture from source code.

This is also where a notebook can become a portfolio without becoming a sales page. A well-scoped explanation demonstrates judgment: what was understood, what was tested, and what remained open. It is more informative than a long list of tools without a connection to decisions. Future project notes should make the work reviewable and give credit to the team, while keeping claims within the evidence available.

Publishing notes responsibly and maintaining them

A public note should make it easy to distinguish the author’s work from source material. Link to the course topic, documentation, or project that informed the explanation. Paraphrase the relevant idea in the context of the exercise, and avoid reproducing gated training material or challenge answers merely to make a page longer. The notebook’s value should come from its own reasoning and examples.

Before publishing, review what the page reveals. Screenshots can contain usernames, internal addresses, access tokens, or browser tabs unrelated to the topic. Logs can include identifiers that are unnecessary for the explanation. A fictional label or a shortened output can often preserve the learning value. Keep the original evidence privately where appropriate, and publish only the portion needed to support the claim.

Maintenance deserves a plan too. A command can stop behaving the same way after a version change. A profile statistic can become outdated. A link can move. Date the observation, state the version when it affects the result, and distinguish a historical description from a current recommendation. A reader should not have to guess whether the page is an archive of an exercise or a guide that is being maintained.

Corrections should improve the explanation openly. If a conclusion was too broad, narrow it and explain what the evidence actually supports. If a command was missing a necessary condition, add the condition near the example. This is more useful than silently accumulating contradictory notes. A notebook can show how understanding develops without presenting every early idea as a finished result.

There is no need to publish every study session. Some sessions produce a question, a partial reproduction, or an unresolved result. Those can remain private until the explanation is coherent. Publishing fewer, clearer notes respects the reader’s time and encourages deeper review. The standard is whether a page helps someone understand a specific system behaviour, not whether a posting schedule has been filled.
