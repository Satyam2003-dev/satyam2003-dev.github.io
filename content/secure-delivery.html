Start with the system the pipeline creates

A CI/CD pipeline is a program that turns one set of inputs into software that other people will trust. Its inputs can include repository changes, package versions, configuration, action code, event metadata, and credentials. Its outputs can include a website, a container image, a package, or a running service. Reviewing that transformation requires more than checking whether the workflow has a security scanner. The important question is which decisions make the output trustworthy.

This article develops an original review method for a small team using GitHub Actions, with examples drawn from a static website and a fictional cloud application. It connects the subject matter of TryHackMe’s Introduction to DevSecOps, SSDLC, and Dependency Management rooms with questions that can be asked during an engineering review. It is a general reference, not a reconstruction of a gated room, an employer’s architecture, or an account of an undisclosed security incident.

Begin by describing the intended outcome in one sentence. For a website, it might be: a reviewed change on the main branch produces a validated set of public files and publishes those exact files to the approved site. That sentence already contains several testable decisions. The change must be reviewed, the branch must be appropriate, the files must be validated, and the published result must correspond to the artifact that passed the checks.

Then draw the stages and the boundaries between them. A useful first diagram is source, build, validation, approval, publication, and live verification. Label each stage with its input, output, and identity. Do not assume that all stages need the same permissions or that every input has the same level of trust. A pull-request build and a production publication may use related code while requiring very different authority.

Source→Build→Validate→Publish→Verify

The rest of the review should connect controls to this description. If a setting cannot be explained in terms of an input, an identity, an artifact, or an outcome, investigate its purpose before treating it as a requirement. A smaller pipeline with understandable boundaries can be easier to assess than a larger pipeline whose many tools obscure the actual publication path.

Build an inventory before adding controls

The first deliverable in a pipeline review should be an inventory. List the workflows that can run, the events that trigger them, the branches they operate on, and the environments they can reach. Include workflows that appear unrelated to deployment, such as release automation, documentation updates, package publishing, or scheduled maintenance. Their access may still affect the repository or the artifacts that a deployment trusts.

For each workflow, identify where code is executed. A shell step executes code, but so does a third-party action, a package install, a build script, or a test suite. The inventory should not stop at visible commands in the YAML file. Follow the commands into the project configuration and record any scripts or tools that run automatically. The purpose is to make the execution path visible enough that a reviewer can ask which inputs influence it.

Next, list credentials and permissions by job. Separate repository access from external access. A repository token, a package-registry credential, a cloud role, and a deployment environment are different relationships. Record why each relationship exists, who owns it, and which operation would fail without it. If nobody can explain why a credential is needed, that uncertainty is a finding to investigate rather than a reason to leave broad access unquestioned.

The artifact inventory deserves equal attention. Identify where outputs are stored, how they are named, how long they are retained, and which later stage consumes them. A directory called build output can still contain source maps, test fixtures, local configuration, or files that were never intended to become public. Define the expected contents rather than trusting a directory name. For a static site, explicitly naming the public output directory makes this decision easier to verify.

Finally, record the owner of the inventory and a trigger for reviewing it again. A new workflow, a changed deployment destination, or a new dependency source can alter the security model. An inventory that is never revisited becomes a historical document. A concise inventory maintained alongside the pipeline can instead serve as the starting point for each significant change.

Separate validation authority from publication authority

GitHub’s secure-use guidance recommends granting the workflow token the minimum permissions required. A practical application is to start with repository read access and grant additional capabilities only to jobs that need them. This reduces the authority available during ordinary build and test execution. It also makes a review easier because the publication permission appears next to the publication job rather than being inherited invisibly by every stage.

# An illustrative permissions fragment, not a complete workflow.
permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Build and validate without publication access"

  deploy:
    needs: build
    permissions:
      pages: write
      id-token: write

The example illustrates a boundary: validation can finish without publication authority. It does not prove that the entire pipeline is secure. The deployment job still needs a review of what it executes, which artifact it consumes, and what its event conditions permit. A narrow permission block is one piece of the design, not a replacement for understanding the surrounding workflow.

For a review, build a small matrix of jobs and required operations. A documentation check may need to read files. A release task may need to publish a package. A deployment may need to update a site. Ask whether those operations can be divided into separate jobs without making the process confusing. The purpose is not to create as many jobs as possible; it is to keep authority near the operation that needs it.

When removing access, define the expected effect first. If a build is supposed to need only read access, it should still produce the expected artifact after write access is removed. If a job fails, investigate the operation it attempted instead of immediately restoring a broad token. The failure may reveal an unexpected write or a tool assumption that deserves a different implementation.

Document exceptions at the same level of detail. If an operation needs an additional capability, record the operation, the resource, the reason, and the owner. A reviewer should be able to tell whether the exception still applies after the workflow changes. This keeps least privilege connected to observable work instead of reducing it to a slogan in a checklist.

Review events and untrusted changes together

A workflow’s event determines the context in which it runs. A push, a pull request, a manual dispatch, and a scheduled run are not interchangeable. GitHub documents the available triggers and their behaviour, including important differences involving pull requests. Review the event alongside the repository state that is checked out and the credentials available to the job. A trigger name alone does not explain the trust relationship.

For a fictional open-source application, a useful policy might be that outside contributions can run validation but cannot publish. Express that policy in a form that can be tested. Define which workflow validates the contribution, which revision it reads, and which publication path remains unavailable. Then examine the whole chain, including reusable workflows and artifacts, rather than looking only for a condition on the final deployment step.

Pay particular attention to privileged workflows that process external input. A workflow may need to inspect a pull request or post a result without needing to execute the proposed code. Those are different tasks. GitHub’s secure-use guidance warns about combining privileged contexts with untrusted code execution. A reviewer should be able to identify where the separation exists and what prevents a contribution from influencing a privileged execution path.

Negative cases are valuable here. What should happen for a fork, a feature branch, a manual run targeting an unexpected revision, or a contribution that changes the workflow itself? Write down the expected outcome before testing. If the observed result differs, preserve the event name, revision, and job conditions in the finding. This evidence is more useful than a generic statement that pull requests are restricted.

Keep the policy understandable to contributors as well. A validation workflow that fails because it cannot access a secret may indicate that the design assumes privileges contributors do not have. Consider whether the test can use a safe fixture or a separate trusted stage. A good boundary should protect publication while still giving an ordinary contributor a clear and useful validation result.

Make dependency selection reviewable

A build depends on code that may not live in the application repository. Packages, actions, toolchains, container bases, and downloaded scripts all influence its behaviour. Treat the selection of these inputs as a reviewable decision. For each important input, record where it comes from, how its version is selected, and how an update becomes part of the build.

GitHub recommends pinning third-party actions to a full commit SHA when seeking an immutable action reference. Keep a readable version comment beside the SHA so a person can understand the intended release while reviewing an update. The SHA alone does not establish that an action is trustworthy; it makes the selected revision explicit. Review the action’s purpose, source, and requested access before allowing it into a privileged job.

Package lockfiles serve a related but distinct purpose. They record a dependency resolution that a package manager can use. For npm projects, the official npm ci documentation describes a clean installation based on the lockfile and a failure when the manifest and lockfile disagree. Use that behaviour as a consistency check, while remembering that a consistent dependency selection can still contain unsuitable or vulnerable packages.

An update review can ask three practical questions. Why is the dependency needed? What changed in the proposed version? What evidence suggests the application still behaves as intended? The answers do not have to be long, but they should be more informative than “the automated update passed.” For a small library change, a targeted functional check may be sufficient. A tool with build-time execution or deployment access deserves a closer examination.

Also examine unnecessary dependencies. A dependency can remain in a project after the feature that required it has been removed. Removing it may simplify the execution path and reduce maintenance work, but the change should still be intentional and validated. Do not turn a security review into uncontrolled cleanup. The inventory should help identify opportunities, and each change should have an explanation and a reviewable result.

Know what the build environment contributes

The source repository is only part of the build input. The runner image, operating system, language runtime, environment variables, and installed tools can affect the result. Decide which of these inputs need explicit versions and which can follow a managed update process. The right level of control depends on the application, but the choices should be visible rather than accidental.

For a learning project, a useful starting record includes the runtime version, the package manager, the command sequence, and the output directory. Reproduce that sequence in a clean environment before adding optimisations. If the build depends on an undeclared global tool or a local configuration file, a clean run can reveal the dependency. This is an engineering check as much as a security check because it helps explain why one environment works and another does not.

Self-hosted runners introduce additional operational responsibilities. GitHub’s documentation describes them as systems the user deploys and manages, including maintenance of the machine and installed software. In a review, identify who maintains the runner, which jobs can reach it, and what resources it can access. A runner connected to important internal systems should not be treated like a disposable machine available to arbitrary contribution code.

Separate the question of convenience from the question of authority. A self-hosted runner may make a build faster or provide a required tool. That does not automatically justify access to deployment credentials or internal networks. Draw the runner as its own component in the trust diagram. List the connections that exist because of the machine’s environment, even if those connections are not visible in the workflow file.

Finally, define what a clean starting state means for the project. It might include a fresh workspace, a reviewed base image, and the absence of files from an earlier job. Avoid claiming that one cleanup command establishes all of these properties. The review should describe the actual isolation and lifecycle of the environment, then identify any assumptions that require additional evidence.

Trace credentials through success and failure paths

A secret is not protected merely because it is stored in a secret-management interface. Trace where it becomes available, which process consumes it, and which outputs can contain it. GitHub’s secrets documentation explains how secrets can be referenced in workflows, while the secure-use guidance notes that masking is not a guarantee for every transformed value or error path. The review must follow the value’s use as well as its storage.

For each credential, describe the intended operation in ordinary language. “Publish this package to this registry” is clearer than “the release secret.” Then identify the job, the resource, and the minimum access required. This makes it easier to distinguish credentials that are still necessary from credentials retained because an old workflow once used them.

Failure paths deserve deliberate review. A tool may print configuration when an operation fails, or a debugging step may expose more context than expected. Study the tool’s behaviour with harmless test values in an authorised environment. Avoid testing by deliberately exposing a real credential. The purpose is to understand where sensitive data could appear and to adjust the handling before the pipeline relies on that path.

Logging should preserve useful evidence without turning the job transcript into a credential store. A deployment can record the resource name, revision, operation, and result without printing the authentication material. If a diagnostic requires more detail, decide which fields are necessary and whether they can be safely represented. A generic request to print every environment variable is rarely a thoughtful investigation method.

Plan the response to exposure before it happens. Identify the credential owner, the system in which it must be invalidated, and the evidence needed to understand the scope. Removing a visible string from a log does not by itself establish that the credential is no longer usable. A documented response should connect containment, credential replacement, and investigation, with actions chosen for the actual incident rather than copied blindly from a template.

Use federation carefully when reaching cloud resources

For workloads, AWS recommends IAM roles and temporary credentials where possible. GitHub’s OIDC integration with AWS provides a way for a workflow to request temporary access without storing a long-lived AWS credential as a repository secret. This changes the authentication mechanism, but it does not remove the need to define who may request the role or what the role may do.

Two separate policies deserve review: the trust relationship that permits an identity to assume the role, and the permissions that the assumed role receives. A carefully scoped permissions policy is insufficient if the trust relationship accepts unintended callers. Likewise, a narrowly defined caller can still receive excessive resource access. Review both sides of the relationship and describe them in the pipeline inventory.

GitHub’s current AWS OIDC guide describes conditions on audience and subject claims, and notes that subject formats can vary with repository settings, including immutable owner and repository identifiers. Use the actual claims and current documentation when designing a trust policy. Do not copy an example for a different repository, event, or environment and assume that changing one visible name makes the relationship correct.

For a fictional application, define the expected caller first: the approved deployment workflow for the intended repository and environment. Then define the expected operations on the intended resources. Prepare positive and negative verification cases that match that description. The negative cases might include an unexpected branch or a different environment. Perform these checks in an appropriate test account with bounded resources rather than experimenting with broad production permissions.

Temporary credentials still require careful handling. Their shorter lifetime is useful, but a credential available during a privileged job can still be misused during that window. Keep untrusted execution away from the job that receives the role, avoid logging credentials, and preserve the identity and operation records needed to investigate a deployment. Federation works best as part of a clear trust model, not as a decorative setting attached to an otherwise unexamined pipeline.

Choose checks that answer specific questions

A pipeline can run many tools while leaving its most important assumption untested. Start each check with a question. Does the application build? Do internal links resolve? Does the package contain only intended files? Does a permission test establish the expected boundary? A check should have a defined input and an outcome that a reviewer can connect to the question.

For a static website, a meaningful validation set might include a production build, content structure, internal links, page metadata, and a browser review of important routes. The browser review catches issues that a successful compiler cannot establish, such as unreadable wrapping or a theme switch that does not work. The structure check catches issues that a screenshot can miss, such as a broken link on a page that was not opened.

For an application, checks should follow its risks. A parser may need tests for malformed input. An authorisation boundary may need tests that distinguish identities. A dependency update may need a targeted regression check. Choose tests because they can detect a relevant failure, not because a pipeline looks more impressive with a larger count. A collection of tests that repeats the implementation’s assumptions can provide false confidence.

Security-tool findings need an interpretation path. Define what blocks a release, who reviews uncertain findings, and how exceptions are recorded. A tool exit code can indicate a scanner failure, a detected issue, or a configuration problem, depending on the tool. Preserve those distinctions. A pipeline that treats an unavailable scan as a clean result has changed the meaning of its own validation without telling the reviewer.

Finally, make failures useful. Report the relevant file, stage, or resource, and explain the expected condition. Keep logs concise enough that a maintainer can find the evidence. The goal is not to make every failure gentle; it is to make the next investigation clear. A well-designed failure helps prevent a hurried maintainer from bypassing a control simply because the control’s result is difficult to understand.

Follow the artifact, not only the source commit

A source commit identifies the code and content in the repository. An artifact identifies the output produced from those inputs. The two are related, but they are not interchangeable. A build can include unexpected files, use a different dependency selection, or depend on an environmental input. A publication review should therefore follow the artifact that was actually validated rather than assuming that the source revision explains the entire result.

For the fictional website, define the artifact as a specific public directory generated by the build. Validation should inspect that directory. Publication should consume that directory’s uploaded artifact. Avoid rebuilding in a later privileged job unless the design deliberately accounts for the second build and its inputs. Keeping the validated output and the published output connected makes the delivery story easier to review.

GitHub’s artifact documentation describes how workflow outputs can be stored and shared between jobs. Use clear artifact names and record the run and revision associated with the artifact. Naming alone is not a trust guarantee, so the consuming workflow still needs to know which producer it accepts. A reviewer should be able to explain why this particular output is eligible for publication.

For more complex software, provenance can help record the relationship between an artifact and its build. The SLSA provenance specification describes structured information about how an artifact was produced. A provenance statement is evidence to evaluate, not an automatic declaration that software is safe. Its usefulness depends on whether the producer is trusted, whether the subject matches the artifact, and whether the recorded inputs answer the review’s questions.

Retention is another practical decision. Keep enough release evidence to investigate a problem or reproduce a relevant output, while avoiding indefinite storage of unnecessary data. Identify which artifact represents the currently deployed version and which earlier version could support recovery. This turns artifact handling into part of operations rather than treating it as temporary storage used only to make a workflow pass.

Keep cache behaviour separate from release evidence

Caches can make repeated builds faster, but speed is not the same as trust. A cache is an optimisation that supplies previously stored data. A release artifact is an output selected for publication. The pipeline design should keep those roles separate. If a maintainer cannot explain whether a file came from a cache, the source tree, or the current build, the investigation becomes harder when a result is unexpected.

GitHub documents cache key matching and cache scope. Review those details for the actual workflow rather than assuming that a key is an exact guarantee of origin. Ask which jobs can create a cache that another job may restore, what data is stored, and whether the build can safely validate or regenerate that data. The questions should be answered before a cache is added to a privileged path.

A useful comparison exercise is to run a build with a fresh cache and a build using the intended cache, then compare the outcomes relevant to the project. Differences should be explainable. The exercise is not a demand that every byte always match: timestamps or deliberately variable data can affect outputs. It is a way to identify where optimisation changes assumptions or introduces state that a clean build did not require.

Avoid storing credentials or unrelated workspace data in a broad cache path. Define the cached directory narrowly and document why its contents are safe to reuse. If the cache is intended only for downloaded dependencies, a review should not discover deployment configuration mixed into the same directory. The boundary is easier to maintain when the directory structure expresses the intended role.

Also plan how to diagnose a cache-related failure. A maintainer should be able to bypass or refresh the cache in a controlled way without changing the application’s release policy. Keep the clean-build command documented. This gives the team a baseline when a fast build behaves differently from an expected result and prevents cache deletion from becoming an unexplained ritual performed whenever a pipeline fails.

Make the publication decision explicit

A successful build establishes only the conditions that the build checked. Publication is a separate decision with a destination and an owner. GitHub environments can apply deployment protection rules to jobs that reference them; the platform’s documentation explains the available features and plan-dependent limits. Choose rules that match the project’s actual review policy instead of assuming that the existence of an environment name creates an approval boundary.

For a personal static notebook, automatic publication from a reviewed main branch may be an appropriate policy. For a company application, publication may require an environment review, a release window, or additional evidence. The important architectural decision is to keep the publication stage separate enough that the policy can grow without giving every validation job production access.

Before publication, establish the intended revision and artifact. After publication, check the destination. This sounds obvious, but it prevents several common misunderstandings: confusing an uploaded artifact with a deployed artifact, confusing a completed workflow with a correct route, or confusing an old cached page with the current release. The verification should observe the product behaviour that users need, not only the deployment tool’s status.

For the website example, verification includes the homepage, an article route, a direct refresh of that route, and the important assets. It also includes the theme control and mobile reading layout. A release can succeed technically while the visitor receives a README, a missing stylesheet, or a blank client-side application. These are failures of the publication outcome even if an intermediate command succeeded.

Preserve the result of the verification with the release evidence. Record the deployed revision, the destination, the observation time, and any material limitation. If a route could not be checked, say so. This does not need to become a large ceremony; a concise, concrete record is enough to distinguish an attempted publication from a release that was actually observed to work.

Prepare for a failed release before relying on rollback

Recovery begins with a definition of what must be restored. For a static site, the previous public artifact may be sufficient. For an application with data migrations or external state, restoring code may not restore the earlier system. A pipeline review should identify these differences before using the word rollback as if it describes one universal action.

Write a small recovery scenario for the project. The website scenario might be that a new release breaks a critical page. Identify the known-good artifact or revision, the person who can publish it, the verification needed afterward, and the expected time constraints. Keep the scenario concrete enough that another maintainer can follow it without reconstructing the release process during the failure.

Then consider what evidence needs to survive the incident. Logs, artifact identifiers, dependency selections, and deployment records can help explain why the release failed. Removing all evidence while trying to recover may make the service usable but leave the cause difficult to investigate. The response should balance restoration with the need to preserve relevant information, chosen for the actual system and incident.

Credential exposure is a different recovery scenario. Reverting a source change does not necessarily invalidate an exposed credential. The response must identify the affected identity, the access it had, and the place where it can be revoked or replaced. This is why credential ownership belongs in the inventory. A clear owner can act faster than a team searching for who created an undocumented secret.

Practise recovery in a suitable test environment when the system warrants it. Record what was learned, including assumptions that did not hold. A recovery document that has never been tried may still be useful, but it should be described as a plan rather than a verified capability. That distinction encourages meaningful rehearsal instead of treating a written procedure as proof that a future incident will be easy.

A review that can be maintained as the team grows

A checklist is most useful when each item points to evidence and an owner. “Use least privilege” is a principle. “The build job has repository read access, and the publication job alone has site publication access” is a reviewable statement. The second statement can be checked against the workflow and revisited when the pipeline changes. Aim for that level of specificity without turning every review into a long compliance document.

  • Which events can run each workflow, and which revisions do they execute?
  • Where can untrusted input affect code execution?
  • Which job receives each permission or credential, and why?
  • Which dependencies, actions, and build tools are selected?
  • What output is validated, and is that exact output published?
  • What prevents an unexpected branch or caller from publishing?
  • How is the destination checked after deployment?
  • Who owns findings, exceptions, and the recovery procedure?

Use the checklist to discuss changes, not merely to approve the pipeline once. A new package registry, a reusable workflow, or a self-hosted runner can introduce a different relationship. Update the diagram and inventory when that relationship changes. A small, accurate model maintained over time is more useful than a detailed model that describes an obsolete design.

As a site grows into a company platform, preserve the separation between presentation, content, build, and publication. New application features may later require a backend, authentication, or storage, but those additions should be designed around their own data and access requirements. A static publication pipeline should not quietly become a privileged application platform simply because a new feature was convenient to add.

The practical outcome of this review method is an explainable delivery path. A maintainer can identify what was accepted, what executed, what was checked, what was published, and what was observed afterward. That explanation does not promise perfect security. It provides a foundation for investigating failures, making narrower changes, and improving the pipeline with evidence as the project and team develop.
